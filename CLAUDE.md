# kreators.app

Seven relationships as a daily game, with a creator super app on top: public site, learn-and-earn modules, content rewards, a shop with attribution, finance, circles, a life dashboard.
Full spec and history: README.md, docs/DECISIONS.md, docs/build-map.html. Read the relevant section before changing anything.

## Stack
pnpm workspace. apps/web: React 19, Vite 7, Tailwind 4, PWA. apps/api: Hono on Cloudflare Workers with D1, plain SQL migrations in apps/api/migrations, cron every fifteen minutes. packages/shared: the domain model both sides import, with Vitest tests.

## Non-negotiable rules
- The product is called kreators.app, lowercase with the dot, in every heading, footer, email, policy and share card; never "Kreators Life". Identifiers keep their old names: the Worker and database `kreators-life`, the `@kreators/*` packages, storage keys and the repo.
- Money is integer cents or integer points. Use `money()` and `feeBps()` from shared. Never floats for money.
- Times are stored as UTC ISO strings. Zone conversion happens only through `zonedToUtc` and `slotsFor` in shared.
- Auth is hand-built on Hono and D1, no package: Bearer session tokens in `sessions` (two UUIDs), PBKDF2-SHA256 at 100,000 iterations (the Workers free-plan ceiling) with a 16-byte hex salt from `randomHex`, constant-time compare. `passwordProblem` in shared is the one password rule, used by the sign-up form, the change form and both endpoints. Sign-in answers the same for an unknown email and a wrong password, hashes against a decoy salt when the email is unknown so the timing matches, and is limited per address and per email by the numbers in `apps/api/src/limits.ts`. `POST /me/password` needs the current password and deletes every other session. `secureHeaders()` runs on every API answer. Password reset: `POST /auth/forgot` answers the same for any email and mails a one-time link (32 random bytes, stored as a SHA-256 hash in `password_resets`, thirty minutes, one open per account); `POST /auth/reset` checks the rule, claims the token, sets the hash and deletes every session. Founder addresses in `apps/api/src/admins.ts` and `ADMIN_EMAILS` get the admin role on sign-up or sign-in (`promoteBootstrapAdmin`, audited); until mail verifies addresses, whoever signs up with one first gets it. Magic links were tried and removed (migrations 0018 and 0019). Sign-up also asks for a phone number and a date of birth (`phoneProblem`, `birthDateProblem` and `MIN_AGE` 18 in shared, migration 0026): nobody under eighteen gets an account, the phone can be changed under Profile, the date of birth cannot, and neither is ever shown to anyone else.
- Every owner-scoped query filters by the session user id. Staff powers come from `can(user, permission)` in apps/api/src/db.ts.
- A switched-off module is refused by the server, not only hidden: `MODULE_FOR_PREFIX` and `modulesForPath` in apps/api/src/access.ts map every API prefix to its module or modules, and the middleware in index.ts answers 403 when none of them is available to the person (global flag, override, rollout or minimum role). The person's own on/off is a preference the client keeps with `Gate`. A new route file gets a line in that map or it is treated as core and always open.
- Rate limits live in one file, `apps/api/src/limits.ts`: `LIMITS` holds every name with its count and window, `ROUTE_LIMITS` says which method and path each one guards, and index.ts wires them (the doors without a session per address before the session check, everything else per person after it). Change a number there and nowhere else; `rateLimit(name)` in ops.ts reads it. Posts, replies, likes, follows, chat messages, offers, listings, tickets, applications and run entries are limited as well as the auth doors.
- Lists are served a page at a time: `PAGE_SIZES` (10, 25, 50, 100) and `Page` in shared; `pageOf(c, prefix)` and `paged(rows, ask)` in db.ts on every list route (one extra row is fetched so `more` says whether a next page exists); `Pager` and `usePage` in `components/Pager.tsx` on the screen (the page lives in the URL, a prefix tells two lists on one screen apart); `page` and `onPage` on `DataTable` for the admin tables. Never a bare `LIMIT 100` on a list a person scrolls.
- Club benefits are code, not words: an opportunity can be `club_only` (migration 0027) and is then listed, opened and applied to only by an approved, unexpired member (`isClubMember` in db.ts), and never shown on the public site; a reviewer names a staff member as a member's manager (`POST /club/memberships/:id/manager`), shown on their Club page and sent to their inbox. A reward can change after launch only through `PATCH /win/:id` (its creator, or review or talent staff): the version goes up, the audit row says what changed, every entrant gets an inbox note, and the pool never drops under what was already paid.
- Payment code talks to apps/api/src/payments.ts, never to a provider SDK directly. A money order becomes `paid` only in the webhook after signature verification.
- Webhooks: verify the signature on the raw body, store the raw payload in `webhook_events`, then process. Duplicates are no-ops.
- The /go redirect writes the click after the redirect is sent and never stores a raw IP, only a salted hash.
- Journal and wellbeing data never reach brands, staff, the leaderboard or Club selection.
- Everything that pays out has a wait or a reviewer: task age, daily tick cap, verified views, finance permission for payouts. A task with a date cannot be ticked before that date: `POST /nodes/:id/complete` takes the person's date and refuses an early tick, and `TaskRow` locks the box with "Tick it on the day".
- Unlocks: a product, a store item or a tool can ask for a points balance, a badge, or both (`min_points`, `badge`, migration 0024). `unlockFor` in shared is the one rule and the one wording; the server computes the viewer's `Unlock` (`badgesNow` plus `honorKeys`) for the product page, every store item and every tool, refuses a gated checkout with 403, and blanks a locked item's or tool's link. Creators set it on their products, staff on items and tools, from the same two inputs (points floor, badge select over `BADGES` and `HONORS`).
- Nudges: one quiet line (`components/Nudge.tsx`, 12px, soft) under the thing it talks about, never a banner, each linking to Help, "How you earn" (`earningGuide` in shared, the one list of what pays). Every app's main screen ends with a "How it works" section (`HowItWorks` in `components/HowTo.tsx`, rendered by `Screen` from the module key that `Gate` and `explained` in App.tsx provide; it shows only when the path is the module's own path, so detail pages inside an app leave it to the main screen) with three to five concrete steps from `HOW_TO`, each a sentence or two with the numbers and the rules, then the words it leans on from `TERMS`. The section is one card that is a button (`toy toy-soft`, lifts and tints on hover, stays tinted while open, closed by default); tapping it opens the steps and the words together, each a smaller flat toggle inside (`toy-flat`, tints on hover, darker while open), and tapping it again folds everything away. Opened content slides in with GSAP (`gsap.set` under reduced motion). Never a floating button or a sheet; the section carries `span-all` so on Home's two-column grid it takes the full width. Help lists every word under "Words we use". A new app gets a `HOW_TO` entry (the shared test insists) and new words go in `TERMS`; a screen that must not show it passes `howTo={false}`.
- Search (`SearchBox`) shows apps and help from the client and tasks, journal, knowledge, products, people, store items, pre-owned listings, tools and community posts from `GET /search`, grouped, under the box as you type. Life's five bars are labelled by name. The public site lists every app a relationship serves and can switch the same section to the five areas of life (`LIFE_AREA_FEATURES`).
- Not to do: at most `MAX_NOT_TO_DO` (7) items a person, titles up to `NOT_TO_DO_TITLE_MAX`; one row per item per day in `not_to_do_days` (kept or slipped; no row means missed). `notToDoStreak` in shared is the one streak rule: today counts once ticked, the run ends at yesterday until then, and a slip or a missed day ends it. A kept day pays `XP.notToDo` once per item per day and is never clawed back. Only today or yesterday can be marked (`dateNearToday`), and the request says which day is the person's today so the streak is counted as of that day. The section sits under Tasks on Daily and is not one of the three boxes; the list is in the export and goes with erase and delete.
- Periods and reviews: `periodFor`, `periodShift`, `periodLabel` and `periodDays` in shared are the one period arithmetic (weeks start on Monday, quarters and halves follow the calendar, both ends inclusive, labels like "19 to 25 Oct 2026"). `GET /reviews/summary` pulls one period's numbers from every app's own table (`numbersFor` in reviews.ts) next to the period before; journal and wellbeing numbers go only to their owner. One review per person per period (`UNIQUE (user_id, kind, period_start)`), saved with the prompts and a snapshot of the numbers so a changed template or new data never rewrites it; a period that has not started is refused. Each cadence has a built-in template in shared (`REVIEW_PROMPTS`, `builtInTemplate`) that cannot be edited or removed; a person's own templates (`review_templates`, up to `MAX_REVIEW_TEMPLATES`) recur with their cadence. `components/PeriodFilter.tsx` is the one period control and `components/PeriodPanel.tsx` (the filter plus `SummaryTiles`) is the "By period" block every dashboard carries: Home, Life, Finance, Wellbeing, Mood, Sleep, Stress, Mindful, Journal and the Shop. Reviews live in the Reflection group, off by default.
- Only spacing values 8, 12, 16, 32, 64, 120 (tokens xs, sm, md, lg, xl, 2xl). Never hardcode hex colours in screens; use the theme tokens so dark mode works. The ink family is grey, not brown: `#262626` (85% black) for ink in light mode, `#121212` paper and `#1e1e1e` card in dark mode, greys for soft, mute, line and edges; the seven relationship colours and their tints keep their hues, including the brown of With yourself, and the icons and share card use the same ink.
- Wording is universal and plain, readable by a teenager (Flesch 60 or above; `python3 -I scripts/flesch.py <file>` scores a file, `--strings` scores only the quoted text of a TypeScript file). The words are: seven *pillars* (never tower, floor or area for the seven; the five *areas of life* keep that word), each pillar is a *pyramid* with six *layers* (foundation, guiding principle, value goal, goal outcome, project, task; never rule, feeling, proof, rung or ladder; the internal kinds pillar, principle, value_goal and outcome stay as keys only), the daily *small act* (never spark), the *not to do* list on Daily (things to stay away from; never habits, vices or avoidances), *reviews* by *period* (a week, a month, a quarter or a half year; the mid-year check-in is the half; never sprint, cycle or retro), the *Daily* tab (never Today as a screen name) and the *Profile* tab (never You; the public page module is *Public page*). - Onboarding is the strategy session (`screens/Session.tsx` at `/session`, from Welcome; the spec is `Strategy Session App Product Spec.md`), eleven cards one at a time: the frame (health, wealth, seven relationships); a placement on the map for each relationship (`MAP_LEVELS`, sixteen named levels from 20 to 540 in three bands, `BAND_STATEMENTS` per relationship, shown as names and never numbers): the *core* where you usually live and the *floor* where you drop under stress, with a line of evidence asked when the core is 400 or over; fears (`FEAR_OPTIONS`, a pillar and whether it drives decisions) and insecurities (a weight out of ten and a pillar), asked early; a scorecard (`SCORECARD`, sliders out of ten) with the behaviour question (days in seven) whenever a relationship scores 8 or more over a floor under Courage; the real day; the focus; the routine; practices; the contract; the optional live call. `placementFlags` in shared is the one rule: a core of 400 or more with no evidence is capped at 350, the floor never sits above the core, a floor under `COURAGE` (200) makes the pillar a *required* month-one focus, and a gap over `VOLATILE_GAP` (150) marks it volatile. `pickFocus` picks at most two: required floors first, then the lowest cores less ten times the insecurity weight sitting there. `settleScore` caps a score of 8 or more at 6 when the floor is under 200 and fewer than four of seven days were courageous. `routineFor` builds the six blocks (`BLOCK_KEYS`) from the real day for a general and an exceptional day, ramping wake-up and lights-out by `RAMP_MINUTES` (30) a week of compliance towards `TARGET_WAKE` and `TARGET_SLEEP`; only the morning block has steps, and the day is done only when every step is ticked. - Social: the Community feed sorts by `FEED_SORTS` (recent, popular by likes, most replies) and filters by `FEED_FILTERS` (everyone, following, mine); a person can be followed from a post (`POST /community/follow/:userId`, the same `follows` table as the public page). Every social action pays through `rewardSocial` in apps/api/src/rewards.ts with the amounts and daily caps in `SOCIAL_REWARDS` (a post 5 xp up to three a day, a reply 2 xp up to five, a like you give 1 xp up to ten; a like on your post pays the author a point, a new follower two, up to twenty a day), each once per thing (`source_id`/`ref`), so unliking and liking again never pays twice. Trust: `trustScore` in shared is the one formula (xp, points earned, best streak, time here, sales with rating, honors; weighted, 0 to 100, four labels), computed server-side by `trustForMany` in one query and shown with `components/TrustBadge.tsx` on the public page header, the product page and every pre-owned listing; nothing in it can be typed in.
- Do not build the white-label app, instalments or native chat transport (see docs/DECISIONS.md). The Store's chat and offers are polled tables, not a transport.

It runs against a second API on port 8788 whose database lives in `scripts/smoke/state` (`wrangler dev --port 8788 --persist-to scripts/smoke/state --test-scheduled`, migrated with `wrangler d1 migrations apply kreators-life --local --persist-to <that dir>`), so the dev database on 8787 never fills with test accounts; `--keep` leaves that server up, `--fresh` wipes its database first. The checks send their own `CF-Connecting-IP` per run so the sign-up and sign-in limits never trip a rerun; the founder account is `founder@smoke.test` with a fixed password. Screenshots (`node scripts/smoke/shoot.mjs [routes]`, puppeteer-core driving the installed Chrome) use the same server unless SHOOT_ORIGIN says otherwise; it clears the service worker first so every shot sees the latest build, SHOOT_MOTION=1 keeps animation on, SHOOT_THEME picks dark, light or both, and a shot can set `width`/`height` (a phone on its side is `desktop: true, width: 844, height: 390`). `scripts/smoke/contrast-probe.js` is its `SHOOT_PROBE` step: it walks every text node, composites its colour onto the real background, and lists anything under 2.2:1. Run it over every route in dark mode after touching colours; the only accepted hits are white captions on the green fill and greyed unearned badges. `scripts/smoke/overflow-probe.js` is the other probe: it reports a page that scrolls sideways and any element that pokes past the screen (unless an ancestor scrolls or clips it). `node --experimental-strip-types scripts/smoke/shots-all.mjs > shots.json` prepares an account with real data behind every detail page and writes the shot list for all 80-odd routes (`SHOOT_TOKEN` reuses that account, `viewport: true` on a shot takes the first screen only); run the overflow probe over it at phone width after touching layout, and it must come back with 0 hits. `node scripts/smoke/drive-signup.mjs` fills and submits the real sign-up form in Chrome against that server and prints the URLs it passed through; a new account must land on `/session`. Tailwind 4 orders `inline-flex` and `inline-block` after `hidden`, so never put one of those on the same element as `hidden sm:…`; give the element the display class only in the variant.
